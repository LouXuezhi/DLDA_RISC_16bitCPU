# 统一 benchmark · Unified benchmark

改微架构之前先跑一遍，改完再跑一遍，看两遍的差。

```sh
make bench-baseline     # 改之前：把当前数字存成 bench/baseline.csv
make bench              # 改之后：再跑一遍，最后一列就是和基线的差
```

每个核 × 每个 cache 延迟各跑一遍（默认 `LATENCY = 1, 2, 4`）。**答案错了就是 FAIL，
性能变差不是** —— 退出码只看正确性，快慢留给人判断。一个算错了的核给出的周期数没有意义。

## 核 · Kernels

| 核 | 动态指令 | 压的是什么 |
|---|---|---|
| `alu` | 51 | 直线 ALU，无访存无分支。每条依赖前一条 → 纯发射吞吐 + `EX→ID` 前递 |
| `fib` | 86 | 每圈一个必中分支，无访存 → 跳转杀指令的代价 |
| `sumn` | 134 | 每圈一次 `LD` 紧跟着用 → load-use 联锁 + 数据存储延迟 |
| `memcpy` | 131 | 每圈一读一写 → 套件里访存最密的 |
| `branchy` | 150 | 数据相关分支，每圈换方向 → 一位预测器 0% 命中的基线 |
| `sum` | 22 | `doc/ISA.md` 的例子。小，留着做对照 |

源码是 `bench/prog/*.s`，用 `bench/asm.py` 汇编。`.hex` 已提交，所以**跑 benchmark 不需要
python**；只有改了 `.s` 才要 `make bench-asm`。汇编器的编码逐字节对过 `doc/ISA.md` 的示例和
`tb/prog/branch.hex`。

## 指标 · Metrics

跑到**停机**为止，不是跑固定周期数。停机就是 `JAL Rx, #0`，在 ID 里看成「跳转目标等于本指令
地址」。计数在看到停机的那个周期冻结，然后空转几十个周期排干流水线，才去对答案。

| 列 | 含义 |
|---|---|
| `cycles` | 放开复位到看见停机指令，之间的周期数 |
| `insts` | 发射的指令数 —— `id_inst != 0` 且 ID 没被暂停的周期数，加上停机那条 |
| `cpi` | `cycles / insts` |
| `stall_if` `stall_id` `stall_ex` `stall_mem` | 按 `ctrl.v` 的优先级归因，四者互斥，和 = 流水线没前进的周期数 |
| `luse` | `id_stallreq` 拉高的周期数，**不管**有没有被更高优先级盖住 |
| `br_wait` | IF 等 PC 改向的周期数 |
| `branches` `taken` | 分支指令数 / 其中跳了的 |
| `jumps` `loads` `stores` | `JAL`/`JALR`、`LD`、`ST` 的条数 |

`insts` 是可以独立验算的：`alu` 是 2 + 12×4 + 1 = 51，`fib` 是 4 + 20×4 + 2 = 86。对不上就是
计数器坏了，不是设计变快了。

## 基线 · Baseline

`b121176`，`bench/baseline.csv`。

| 核 | lat=1 周期 | CPI | lat=2 CPI | lat=4 CPI |
|---|---|---|---|---|
| `alu` | 103 | 2.01 | 3.01 | 5.01 |
| `fib` | 211 | 2.45 | 3.48 | 5.51 |
| `sumn` | 331 | 2.47 | 4.20 | 6.70 |
| `memcpy` | 389 | 2.96 | 4.94 | 7.92 |
| `branchy` | 411 | 2.74 | 4.29 | 6.73 |
| `sum` | 51 | 2.31 | 4.00 | 6.45 |

三件事这张表直接读得出来：

1. **取指是当前的瓶颈，不是冒险。** `alu` 没有访存没有分支没有联锁，CPI 还是 2.01 ——
   `if_stage.v` 的握手每取一条指令要两个周期（发 `imem_re` 那个周期 `stallreq = 1`，
   下个周期才拿到指令），下一次取指不和这一次重叠。`alu` 的 CPI 精确等于 `LATENCY + 1`：
   1→2.01，2→3.01，4→5.01。取指完全串行，一点重叠都没有。
2. **一次跳转多花约 2 个周期。** 拿 `alu` 当没有跳转的对照：103 / 51 = 2.02 周期每条。
   `fib` 86 条按这个价钱是 173.7 周期，实际 211，其中 1 个周期是那条 `ST` 的访存暂停，
   剩下 (211 − 173.7 − 1) / 19 = 1.9 —— 每次跳转 1 个 `br_wait`（等 PC 改向）加 1 个
   重取被冲掉那条指令。`branchy` 那个 `BGE` 每圈换方向，47 次跳转，是留给分支预测的靶子。
3. **load-use 联锁现在是死逻辑。** 所有核的 `luse` 都是 0。因为每条指令之间本来就有一个取指
   气泡，`LD` 从来不会和它的消费者同时分别待在 EX 和 ID 里 —— MEM 的暂停已经把消费者拖住了。
   **一旦取指瓶颈被修掉，`luse` 就会变成非零**，那时 `id_stage.v` 里那段联锁才第一次真的开始
   工作。所以这一列是修取指时的一个正确性信号，不只是性能指标。

## 加一个核 · Adding a kernel

1. 写 `bench/prog/<名字>.s`，末尾 `HALT Rx` —— **`Rx` 挑一个不查的**，`JAL Rx,#0` 每圈都写它。
2. `make bench-asm`
3. 在 `bench/bench.list` 里加一行：名字、程序、数据（没有写 `-`）、周期上限、期望值。
4. **期望值照算法算，不要从 RTL 上抄。** 从 RTL 抄下来的期望值只能证明 RTL 等于它自己。
5. 加完之后把它该抓的东西故意弄坏一次，确认它真的 FAIL（`testbench/README.md` 那两个习惯）。

## 探针 · Probes

`bench/tb_bench.v` 顶上那一块 `wire` 是**唯一**引用设计内部信号的地方，改微架构时只需要改那里：

| 探针 | 引用 |
|---|---|
| 暂停归因 | `dut.ctrl_stall`、`dut.{if,id,ex,mem}_stallreq` |
| 发射 / 分类 | `dut.id_inst` |
| 停机检测 | `dut.id_br`、`dut.id_br_addr`、`dut.id_pc` |
| `br_wait` | `dut.u_if_stage.waiting_for_br_ready` —— 唯一伸进级内部的一个 |

`br_wait` 是这几个里最脆的：重写 IF 就得改它，或者把它去掉。别的都只看 `cpu_core` 顶层。
